# Architecture

zed-react is organized in **four layers**. Each layer may import only from the layers below it.
ESLint enforces this, so an accidental shortcut fails `npm run lint` and the pre-commit hook.

```
 ┌──────────────────────────────────────────────────────────────┐
 │ app/        composition root: registry, router, shell, ⌘K    │  knows every feature
 ├──────────────────────────────────────────────────────────────┤
 │ features/   auth · dashboard · tasks · users · settings      │  never import each other
 ├──────────────────────────────────────────────────────────────┤
 │ core/       api · auth · router · i18n · query · theme ·     │  knows no feature
 │             forms · notify · layout · config · feature       │
 ├──────────────────────────────────────────────────────────────┤
 │ shared/     ui (shadcn) · components · hooks · lib           │  knows nothing about this app
 └──────────────────────────────────────────────────────────────┘
   mocks/   fake backend: may read core/config only
   testing/ test helpers: may import anything
```

## The layers

### `shared/`: generic building blocks

Code you could copy into a different project unchanged:

| Folder               | Contents                                                             |
| -------------------- | -------------------------------------------------------------------- |
| `shared/ui/`         | shadcn/ui primitives, generated by the CLI (don't hand-edit much)    |
| `shared/components/` | Generic compositions: `PageHeader`, `Pager`, `ConfirmDialog`, `Kbd`… |
| `shared/hooks/`      | `useDisclosure`, `useDebounce`, `useIsMobile`                        |
| `shared/lib/`        | `cn`, `format` (dates), `storage` (safe localStorage)                |

**Rule:** no imports from `core`, `features` or `app`. No translations and no API calls.

### `core/`: application infrastructure

Everything app-wide that isn't a business feature. One folder per concern:

| Folder               | Responsibility                                                             |
| -------------------- | -------------------------------------------------------------------------- |
| `core/api`           | HTTP client (axios adapter), `ApiError`, shared Zod schemas (`paginated`)  |
| `core/auth`          | Session queries/mutations, `RequireAuth`/`RequireGuest`, roles & policies  |
| `core/config`        | Validated env vars, site metadata, the typed **route table**               |
| `core/feature`       | The `defineFeature` contract between features and the app                  |
| `core/forms`         | `TextField`, `FormFieldError` (translated validation messages)             |
| `core/i18n`          | i18next setup, languages, the `common` namespace, `useTranslation` adapter |
| `core/layout`        | `Page` and `Head`, the standard page frame                                 |
| `core/notify`        | Toast adapter (`notify.success/error/info`)                                |
| `core/observability` | `reportError()`, the single place to plug in Sentry or similar             |
| `core/query`         | Query client factory, global error handling, mutation `meta` side effects  |
| `core/router`        | Router adapter (re-exports routing primitives)                             |
| `core/theme`         | Theme config, store, engine, customizer UI                                 |

**Rule:** no imports from `features` or `app`. Core may use `shared`.

### `features/`: business features

Each feature is a folder with a **public manifest** (`index.ts`) and private internals:

```
features/tasks/
├── index.ts          PUBLIC: defineFeature({ id, routes, nav, commands, i18n })
├── model/            Zod schemas → types, constants, policies (pure, no React)
├── api/              request functions + query options/hooks
├── hooks/            feature-specific hooks (e.g. URL filters)
├── components/       UI used by this feature's pages
├── pages/            route components, lazy-loaded (+ optional `loader`)
├── i18n/             en.json, es.json → the "tasks" namespace
└── __tests__/        integration tests
```

Not every feature needs every folder. `auth` has no `api/` (the session is in core), and
`users` has no `components/`.

**Rules:**

- A feature never imports another feature. If two features need the same thing, move it down to
  `core` (app-specific) or `shared` (generic). If a page needs two features, compose them in `app`.
- A feature never imports `app`, `mocks` or `testing` (except in its tests).
- The app imports a feature **only through its manifest** (`@/features/tasks`), never
  `@/features/tasks/components/...`. The folder's internals stay private, so you can refactor them
  freely.

### `app/`: composition root

The only layer that knows every feature:

| File                  | Role                                                               |
| --------------------- | ------------------------------------------------------------------ |
| `modules.ts`          | **The module registry**: the one list of enabled features          |
| `registry.ts`         | Pure helpers: nav/commands/routes/translations + `validateModules` |
| `routes.tsx`          | Builds the route tree from the registry                            |
| `router.tsx`          | Creates the browser router                                         |
| `providers.tsx`       | Error boundary, query client, tooltips, toasts, devtools           |
| `i18n.ts`             | Registers `common` + every feature namespace                       |
| `i18n-resources.d.ts` | Type registration for translation keys                             |
| `shell/`              | App shell, sidebar, user menu, ⌘K command menu, auth shell, logo   |
| `pages/`              | App-level pages: landing, 404, error and forbidden screens         |

## How a request for `/app/tasks` flows

```
URL /app/tasks
  └─ app/routes.tsx           RequireAuth → AppShell → lazy(tasks manifest route)
       └─ tasks/pages/tasks-page.tsx
            loader()          prefetches tasksQuery(filters)  ← runs while the JS chunk loads
            useTaskFilters()  parses ?page=&q=&status= with Zod
            useTasks()        → tasksApi.list() → core/api/client → axios → /api/tasks
                                                   └─ Zod validates the response
```

## The two "swap" mechanisms

1. **Feature modules** make features pluggable. See [Feature modules](feature-modules.md).
2. **Adapters** make libraries replaceable. Each library is imported in exactly one place.
   See [Swapping libraries](swapping-libraries.md).

## What ESLint enforces

| Rule                     | Error you'll see                                         |
| ------------------------ | -------------------------------------------------------- |
| Layer direction          | `core/ is feature-agnostic: it must not depend on…`      |
| Features are isolated    | `Features must not import each other…`                   |
| App uses manifests only  | `Import a feature's manifest ('@/features/<name>') only` |
| Libraries via adapters   | `Import from "@/core/notify/notify" instead…`            |
| No deep relative imports | `Use the "@/..." alias…` (for `../../`)                  |
| No import cycles         | `import-x/no-cycle`                                      |

The rules live in [`eslint.config.js`](../eslint.config.js). Feature folders are discovered
automatically, so new features are covered without editing the config.

## Design decisions

- **Why manifests instead of a central route file?** Adding or removing a feature touches only
  its folder plus one registry line. Nothing in the shell has to change.
- **Why Zod on responses?** TypeScript types disappear at runtime. A renamed field from the
  backend would otherwise reach a component as `undefined`. Validation turns it into one clear
  `ApiError` with `code: 'contract'`.
- **Why is the session in `core` and not in `features/auth`?** The router, the shell and several
  features need it. The auth _feature_ only owns the sign-in/sign-up screens.
- **Why no barrel files?** Except for each feature's manifest, imports point to the actual file.
  That keeps code-splitting effective and import cycles visible.
